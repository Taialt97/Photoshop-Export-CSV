The Pipeline Breakdown

Photoshop CSV Export & Spine CLI tooling — understand it, explain it, defend it.

What problem does this solve?

A slot game PSD holds hundreds of assets: symbols, jackpots, UI, banners. Before this tool, getting them into the game meant an artist manually selecting, cropping, resizing and exporting each one — for every game, at every revision. Hours of error-prone clicking.

The idea: describe the export once, in a CSV file. One row = one output image. Run the script, get every asset — sized, padded, named, and sorted into folders — in one click.

Before

Select layer → crop → resize canvas → export → rename → repeat ×300. Any layer reorder in the PSD breaks your habits. New game = start over.

After

Write (or reuse) a CSV manifest. Run script. 300 files appear, correctly sized and named, in the right subfolders. The CSV doubles as documentation of what the game needs.

The one-sentence pitch

"It's a manifest-driven exporter: a CSV file declares exactly which layers to export and how — one row per image — and the script does everything else on a safe duplicate of the document."

Key word: declarative. The artist declares what they want; the script owns how.

Built on the shoulders of a giant

The base is antipalindrome/Photoshop-Export-Layers-to-Files-Fast — a popular open-source script that exports all layers of a document as separate files, positionally (layer #1 → file #1, etc.).

That base gave me for free: the ExtendScript plumbing (dialogs, progress bar, preferences), fast layer traversal, and battle-tested save routines for PNG/JPG/TIFF and more.

The journey of one CSV row

Key concepts, one by one

1 — Path grammar: how a row finds its layer

A Path is read top-down through the Layers panel, like a file path: Jackpots/grand, LowSymbols/[0], Wild/[1]/Text.

Two segment types: a name (matched against trimmed layer names — Photoshop names love trailing spaces) or an index [n] where [0] is the TOP item in the panel, counting layers and groups together.

The resolver (resolveCsvPath) is ~25 lines: split on /, walk down, at each level find the child by name or index. If any segment fails → the row is reported as unresolved and skipped, never crashing the run.

Subtlety worth mentioning: only exactly [digits] is an index. Symbols [ALL] is a name — brackets included.

2 — fit vs canvas: the sizing contract

fit (default): scale the asset to fit inside (W−pad×2) × (H−pad×2), then center it on an exact W×H canvas. Use for symbols that must fill a slot cell with breathing room.

canvas: keep the asset's original pixels, center on W×H, crop overflow. Use for pixel-perfect sprites where scaling would blur.

Empty W/H = natural size: no resize, no fixed canvas. Try all three in the Playground tab.

3 — Folder = flatten. Always.

If a Path lands on a group, the whole group becomes one image. Want each child separately? Write one row per child. Deliberate design: every output file traces back to exactly one row — no magic expansion, no surprises.

4 — Scopes: one manifest, many groups

A scope: Jackpots, LowSymbols line before the header makes every row resolve relative to each scope root in turn, and each scope writes into its own subfolder (OUT/Jackpots/…). One generic manifest can serve every symbol set in the document.

Under the hood, out-of-scope top-level groups are pruned from the duplicate before export — smaller doc, faster ops — and scope roots are re-found by stable layer id, not index, so pruning can't invalidate them.

The Spine CLI scripts — same philosophy, different engine

Spine (Esoteric Software) ships a command-line interface: everything the editor's export dialog does can be driven headlessly from a terminal, configured by an export-settings JSON. My Python scripts wrap that CLI into batch pipelines. The philosophy is identical to the Photoshop script: declare once, run everywhere, never touch the source file.

Script 1 — Batch multi-scale exporter (HD/MD/SD)

The studio needs every character at three scales in a required format. The pattern:

# the standard Spine CLI batch pattern
for project in find_spine_files(input_dir):      # 1. discover .spine files
    for scale, suffix in [(1.0,"HD"), (0.66,"MD"), (0.33,"SD")]:
        settings = load_json("export_template.json")  # 2. one template...
        settings["scale"] = scale                       # 3. ...patched per run
        settings["output"] = out_dir / suffix
        run([SPINE_APP, "--update", VERSION,            # pin editor version!
             "--input", project, "--export", settings_path])

Points to explain confidently: the export JSON is the contract (atlas packing, format, scale live there); the CLI's --update flag pins the Spine editor version so every artist's export is identical; Python just orchestrates — discovery, JSON patching, subprocess calls, and error collection.

Script 2 — Spine → MP4 renderer

Two-stage pipeline: Spine CLI can't write video, but it can export image sequences.

# stage 1: Spine CLI renders each animation to a PNG sequence
spine --input char.spine --export png_sequence.json
# stage 2: ffmpeg assembles frames into consistent, centered video
ffmpeg -framerate 30 -i frame_%04d.png -pix_fmt yuv420p out.mp4

Why it exists: animators and stakeholders need to review animations without opening Spine. Auto-rendering every animation to a centered, consistent MP4 turns review into "scrub a folder of videos".

Script 3 — Clean Spine Alpha

Additive-blend textures exported as WebP showed white fringing — edge pixels where RGB values leak from transparent areas. The script batch-processes textures to clean those halo artifacts. The interview-friendly explanation: "additive blending multiplies color by alpha at runtime; any non-black RGB hiding in fully-transparent pixels becomes a visible glow halo — the script sanitizes those pixels in bulk."

⏱ Deep dive (tech artist / developer) — likely questions

"How do you avoid exporting a black background behind transparent assets?"

Two things. Photoshop's locked Background layer can't be hidden, so it's demoted to a normal layer on the duplicate first (neutralizeBackgroundLayer). And groups are never merge()d — merging a Pass-Through group bakes a black backdrop — instead the group is isolated (everything else hidden) and the save's composite does the flattening, preserving transparency.

"What happens when a row is wrong?"

Nothing dramatic — that's the point. A validation pass resolves every row before any export; unresolved rows are skipped and listed in the end-of-run summary alongside collisions and bad scopes. One typo never kills a 300-row run.

"Why don't layer effects break when you resize?"

Live layer styles re-render at the new size — a 10px drop shadow stays 10px after downscaling, which looks wrong. So the script rasterizes the style into pixels at native scale first (via ActionManager, since the DOM has no API for it), then crops and resizes flat pixels.

"How is state kept clean across hundreds of rows?"

Each row is wrapped in history snapshot/restore, so crops and resizes are undone after saving; visibility (which history doesn't cover) is reset by re-hiding everything; and stale object references are avoided by re-resolving paths live per row and re-finding scope roots by stable layer id rather than index.
